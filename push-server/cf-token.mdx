## What it does

`cf-token` is a lightweight token service that issues short-lived RS256 JWTs to bridge clients. It also exposes a JWKS endpoint so `cf-push-relay` can verify tokens independently without calling back to cf-token.

## API

### `GET /health`

Health check. No authentication required.

```json
{ "ok": true, "status": "healthy", "timestamp": "2026-01-01T00:00:00.000Z" }
```

---

### `GET /.well-known/jwks.json`

Returns the RS256 public key in JWK Set format. Used by `cf-push-relay` to verify JWTs offline.

```json
{
  "keys": [
    {
      "kty": "RSA",
      "use": "sig",
      "alg": "RS256",
      "kid": "key-id",
      "n": "...",
      "e": "AQAB"
    }
  ]
}
```

Response is cached for 1 hour (`Cache-Control: public, max-age=3600`).

---

### `POST /token`

Exchange client credentials for a JWT. This is the only endpoint Aptove Router calls.

**Request body:**

```json
{
  "client_id": "your-client-id",
  "client_secret": "your-client-secret"
}
```

**Response:**

```json
{
  "access_token": "eyJ...",
  "token_type": "Bearer",
  "expires_in": 3600
}
```

**JWT claims:**

| Claim | Value |
|-------|-------|
| `iss` | `TOKEN_ISSUER` env var |
| `sub` | `client_id` |
| `aud` | `TOKEN_AUDIENCE` env var |
| `iat` | Issued-at timestamp |
| `exp` | `iat + 3600` |
| `scope` | `"push:write"` or `"admin"` |

---

### `POST /clients` *(admin only)*

Create a new bridge client. Returns a generated `client_secret` — store it securely, it is not recoverable.

**Headers:** `Authorization: Bearer <admin-jwt>`

**Request body:**

```json
{
  "client_id": "my-bridge-client",
  "scope": "push:write"
}
```

**Response (201):**

```json
{
  "ok": true,
  "client_id": "my-bridge-client",
  "client_secret": "generated-secret"
}
```

---

### `DELETE /clients/:id` *(admin only)*

Revoke a client. Any JWTs already issued for this client will still be valid until they expire.

**Headers:** `Authorization: Bearer <admin-jwt>`

```json
{ "ok": true, "message": "Client deleted" }
```

## Environment variables

| Variable | Where set | Description |
|----------|-----------|-------------|
| `RS_PRIVATE_KEY` | `wrangler secret` | RS256 private key in PKCS#8 PEM format |
| `ADMIN_CLIENT_SECRET` | `wrangler secret` | Secret for the built-in admin client |
| `TOKEN_ISSUER` | `wrangler.toml` `[vars]` | `iss` claim in issued JWTs (e.g. `"https://token.aptove.com"`) |
| `TOKEN_AUDIENCE` | `wrangler.toml` `[vars]` | `aud` claim in issued JWTs (e.g. `"https://push.aptove.com"`) |
| `ADMIN_CLIENT_ID` | `wrangler.toml` `[vars]` | Built-in admin client ID — change from `"admin"` before deploying |
| `TOKEN_BUCKET_CAPACITY` | `wrangler.toml` `[vars]` | Max burst size for `/token` rate limit (default: `"5"`) |
| `TOKEN_REFILL_INTERVAL_MS` | `wrangler.toml` `[vars]` | Ms between token bucket refills (default: `"3600000"` = 1hr) |
| `CLIENT_REGISTRY` | `wrangler.toml` `[[kv_namespaces]]` | KV namespace binding for storing client records |

## Rate limiting

Every endpoint has rate limiting to prevent abuse and brute-force credential testing.

| Tier | Mechanism | Purpose | Cost |
|------|-----------|---------|------|
| **Tier 1 — Abuse ceiling** | Cloudflare native `[[ratelimits]]` binding | Hard cutoff for burst abuse/DoS | Zero (no KV) |
| **Tier 2 — Token bucket** | KV-backed token bucket | Sustained rate control with configurable burst | 1 KV read + 1 KV write per request |

### Per-endpoint limits

| Endpoint | Tier 1 (Cloudflare native) | Tier 2 bucket capacity | Tier 2 refill rate | Sustained max |
|----------|----------------------------|------------------------|--------------------|--------------:|
| `POST /token` | 1 req/min per `client_id` | 5 | 1 token per 1 hr | 1/hr |
| `GET /health` | 1 req/min per IP | — | — | 1/min |
| `GET /.well-known/jwks.json` | 1 req/min per IP | — | — | 1/min |

### Brute-force protection

Rate limiting on `POST /token` fires **before** the PBKDF2-SHA256 credential verification. This is critical: without it, an attacker could test secrets at high speed against the computationally expensive PBKDF2 check. With rate limiting, they are limited to 1 attempt per minute (Tier 1) and 1 sustained attempt per hour (Tier 2).

### Token bucket algorithm

Same implementation as cf-push-relay. Each client gets a bucket with a fixed capacity. Every request consumes one token. Tokens refill at a constant interval up to the capacity.

```
KV key:  rl:token:{client_id}
TTL:     24 hours (auto-cleanup)
```

### Configuration

```toml
[vars]
TOKEN_BUCKET_CAPACITY = "5"            # max burst size
TOKEN_REFILL_INTERVAL_MS = "3600000"   # 1 hour between refills
```

### Expected usage pattern

Aptove Router caches JWTs for ~1 hour and fetches a new one when < 60 seconds of TTL remain. Normal usage: **1 token request per bridge per hour**. The 5-token burst capacity handles startup scenarios where multiple bridges come online simultaneously.

## KV storage

Client records are stored in the `CLIENT_REGISTRY` KV namespace. Each key is the `client_id`; the value is a JSON object with a PBKDF2-SHA256 hashed secret and scope:

```json
{
  "hashed_secret": "<base64 PBKDF2-SHA256 output>",
  "scope": "push:write"
}
```

## Deployment

### Manual

```bash
cd cf-token
npm ci
npx wrangler deploy
npx wrangler secret put RS_PRIVATE_KEY       # paste PEM from scripts/generate-keys.mjs
npx wrangler secret put ADMIN_CLIENT_SECRET  # openssl rand -hex 32
```

### Automated (GitHub Actions)

The repository has a `.github/workflows/deploy.yml` that deploys on every version tag:

```bash
git tag v1.0.0
git push origin v1.0.0
```

The workflow runs `npm run typecheck`, `npm test`, then deploys. Configure two GitHub Actions secrets:

| Secret | Value |
|--------|-------|
| `CLOUDFLARE_API_TOKEN` | API token with Edit Workers permission |
| `CLOUDFLARE_ACCOUNT_ID` | Your Cloudflare account ID |

## Key rotation

To rotate the RS256 signing key:

1. Generate a new key pair: `node scripts/generate-keys.mjs`
2. Update the secret: `npx wrangler secret put RS_PRIVATE_KEY`
3. Deploy: `npx wrangler deploy` (or push a tag for CI)

After rotation, the JWKS `kid` changes. Any JWTs issued with the old key will fail verification. `cf-push-relay` detects the unknown `kid`, invalidates its JWKS cache, and re-fetches automatically. Aptove Router re-fetches a new JWT on the next push request.

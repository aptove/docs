This page covers the trust model of a paired device, what different transport modes protect against, and the resource limits that guard against abuse.

---

## Threat model

### What a paired device can do

Pairing grants a device a long-lived bearer token. Any client that presents that token can:

- Send arbitrary prompts to the agent process — including prompts that ask it to run shell commands, read and write files, or make network requests.
- Browse directories and read file contents (via the `bridge/files/*` protocol).
- Schedule tasks that fire prompts automatically.
- Append to the agent's persistent memory.

The agent process runs as the host OS user. Its reach is exactly whatever that user can do on the machine. **Aptove Router does not sandbox the agent.** A paired phone has, in effect, the same reach as the person sitting at the keyboard.

### If your phone is stolen

The bearer token is stored in the iOS Keychain, encrypted by the device passcode and biometrics. An attacker who obtains the unlocked phone — or who extracts the Keychain by other means — has full agent access until the token is rotated.

**Tokens do not expire on their own.** To cut off access immediately:

1. Open the Aptove Router TUI and run `/rotate-token`.
2. The old token is invalidated within seconds; any reconnect attempt from the stolen device receives **HTTP 401**.
3. Re-pair your remaining devices by scanning the new QR code.

See [Rotating the Auth Token](/aptove/rotate-token) for the full procedure, including how to remove a stolen device's push token from the relay.

### Transport security

Each transport mode defends against a different attacker profile:

| Transport | Protected against | Not protected against |
|-----------|------------------|----------------------|
| **Local** | Internet-side attackers (the port is behind NAT and never intentionally exposed); post-pairing LAN eavesdroppers (TLS with cert fingerprint pinned at pairing time) | Someone on the LAN who intercepts the QR code and races to claim the one-time pairing code before you do; anyone who already holds a valid bearer token |
| **Tailscale** | Internet attackers; LAN eavesdroppers; passive traffic interception (WireGuard encrypts all tailnet traffic end-to-end) | Other Tailscale users on the same tailnet who discover your machine's MagicDNS hostname; anyone who already holds a valid bearer token |

The bearer token is the last line of defence in both cases. Keep the QR code off shared screens and rotate the token if a device is lost.

### Out of scope

The following are not mitigated by Aptove Router and must be managed at the host or network level:

- **Agent sandboxing** — the agent process inherits the full permissions of the host OS user. Restrict this at the OS level (a dedicated low-privilege user, macOS sandbox profiles, container isolation) if that matters for your threat model.
- **Multi-user access control** — there is one shared token, not per-user accounts. Everyone who pairs has equal access.
- **Prompt injection** — a malicious document or web page that the agent reads could try to hijack the agent's actions. Aptove Router does not inspect or filter agent outputs.
- **Tailscale admin access** — a Tailscale network administrator who can manipulate routing could affect reachability. Tailscale itself provides WireGuard encryption between peers.

### Reporting a vulnerability

Security issues can be reported by e-mail to **saltukalakus@gmail.com**. Please allow one week for a response. Responsible disclosures are kept confidential until a patch is released.

The full security policy, including supported versions and responsible-disclosure terms, is in [`SECURITY.md`](https://github.com/aptove/aptove/blob/main/SECURITY.md) in the Aptove repository.

## Resource limits

Aptove Router enforces the following limits to protect against memory exhaustion, oversized inputs, and abuse.

## 1. WebSocket message size (`ws_max_message_mb`)

**Protects against:** memory exhaustion caused by an oversized message from a connected client.

When the mobile app sends a prompt that includes images, each image is base64-encoded inside a JSON message. A single full-resolution iPhone photo is 3–5 MB raw, which becomes roughly 4–7 MB base64-encoded. A prompt with several photos can easily reach 20–50 MB.

| Setting | Default | Unit |
|---------|---------|------|
| `ws_max_message_mb` | `50` | megabytes |

Set this in `common.toml`:

```toml
# Maximum WebSocket message size (default: 50 MB).
# Increase if users send many large images in a single prompt.
ws_max_message_mb = 50
```

**What happens when exceeded:** the WebSocket layer rejects the oversized frame and closes the connection with a protocol error. The Aptove Router process does not crash and no memory spike occurs.

---

## 2. Persistent memory file size (`memory_max_kb`)

**Protects against:** unbounded growth of `MEMORY.md`, which is injected into every new agent session. A very large file would consume a disproportionate share of the agent's context window on every session start.

| Setting | Default | Unit |
|---------|---------|------|
| `memory_max_kb` | `1024` | kilobytes |

Set this in `common.toml`:

```toml
# Maximum size of MEMORY.md (default: 1024 KB = 1 MB).
memory_max_kb = 1024
```

**Behaviour at thresholds:**

| Threshold | Behaviour |
|-----------|-----------|
| **≥ 80%** of limit | `WARN` log emitted on each attempted append |
| **= 100%** of limit | `ERROR` log emitted; append is **blocked**; connected mobile client receives a `bridge/memoryLimitReached` notification with instructions |

When the limit is reached at session start, the injection is skipped (with a `WARN` log) and the session starts without persistent context.

See [Persistent Memory](/aptove/memory) for details on how to clear or increase the limit.

---

## 3. Webhook URL token length

**Protects against:** oversized URL tokens causing log bloat or buffering overhead in the HTTP handler.

| Limit | Value | Configurable |
|-------|-------|--------------|
| Maximum token length | 256 characters | No |

This limit is hardcoded. Legitimate webhook tokens are never anywhere near this length. If the path token exceeds 256 characters Aptove Router returns `400 Bad Request` immediately and closes the connection.

---

## 4. Pairing code rate limit

**Protects against:** brute-force attempts to guess a valid pairing code.

| Parameter | Value | Configurable |
|-----------|-------|--------------|
| Max failed attempts per code, per source IP | 5 | No |
| Code lifetime | 60 seconds | No |

After 5 failed verification attempts **from the same IP address** the current code is invalidated for that address. Codes automatically renew every 60 seconds, at which point the QR code displayed in the TUI updates. The renewed code resets all per-IP counters.

**Reverse-proxy support:** When Aptove Router sits behind a local reverse proxy (e.g. nginx on localhost), the `X-Forwarded-For` or `X-Real-IP` header is used as the effective client IP, so each upstream device gets its own counter. Forwarding headers are only trusted when the TCP connection arrives from a loopback address (`127.0.0.1` / `::1`).

**Tailscale limitation:** `tailscale serve` does not inject `X-Forwarded-For`. All tailnet peers connect through `127.0.0.1` with no forwarding header, so the 5-attempt counter is shared across the entire tailnet rather than per-device. If a misconfigured or misbehaving device on your tailnet exhausts the limit, use `/qr` in the Aptove Router TUI to generate a fresh code and reset all counters immediately — no restart needed.

---

## 5. WebSocket connection rate limit per IP

**Protects against:** connection flooding from a single IP address.

| Parameter | Value | Configurable |
|-----------|-------|--------------|
| Max concurrent connections per IP | 10 | No |
| Max connection attempts per minute per IP | 30 | No |

Connections that exceed either limit are rejected immediately at the TCP accept stage, before any HTTP or WebSocket processing.

**Tailscale limitation:** These limits are enforced on the TCP source address. Under `tailscale serve`, all tailnet devices connect through `127.0.0.1`, so the 10-connection and 30-attempts-per-minute limits are shared across the whole tailnet rather than per-device. For typical usage this is not a problem — normal Tailscale clients do not connect 30 times per minute. If stricter per-device isolation is required, enforce it via [Tailscale ACLs](/aptove/tailscale-transport#access-control-on-shared-tailnets).

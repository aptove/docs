---
title: "Aptove Router Identity & Agent ID"
description: "How Aptove Router identifies itself to connected clients and why bridgeAgentId is the primary identity key."
---

Every ACP session is wrapped by an Aptove Router-specific protocol layer that operates in the `bridge/*` JSON-RPC namespace. These messages are handled entirely by Aptove Router — they are never forwarded to the underlying agent process. This page explains the identity part of that layer.

---

## Why bridgeAgentId exists

Aptove Router binds to a TCP port (e.g. `0.0.0.0:8765`). IP:port is a transport address — it can be reused by any Aptove Router instance that starts on the same machine. If a new Aptove Router instance starts at the same address that a previous one used, the iOS app's auto-connect logic would silently attach the old agent to the new Aptove Router instance. The old agent would then send its stored `cwd` to the wrong instance, making the AI assistant operate in the wrong project directory.

`bridgeAgentId` solves this. It is a stable UUID stored in `common.toml` under `.aptove/` in the project directory. Each project directory gets a different UUID. The UUID survives restarts of the same Aptove Router instance but changes if you move to a different directory.

| Key | Value |
|-----|-------|
| Source | `CommonConfig.agent_id` in `common.toml` |
| Scope | One per working directory |
| Lifetime | Permanent (generated once, never regenerated) |
| Purpose | Primary identity for Aptove Router ↔ iOS agent matching |

## Connection handshake

Immediately after the WebSocket connection is authenticated, before any ACP message is exchanged, Aptove Router sends a `bridge/identify` notification. This is the pre-ACP Aptove Router handshake.

```json
{
  "jsonrpc": "2.0",
  "method": "bridge/identify",
  "params": {
    "bridgeAgentId": "3f2a1b4c-...",
    "cwd": "/Users/alice/code/my-project"
  }
}
```

The mobile client checks `bridgeAgentId` against the value it stored when it first paired with this Aptove Router instance. If they match, the connection proceeds normally. If they differ, the client disconnects immediately and shows an actionable warning:

> **A different Aptove Router instance is now at this address (project: /path/to/other-project). Scan its QR code to add it as a new agent.**

The user can then scan the QR code of the new Aptove Router instance to add it as a second agent, keeping both projects independent.

---

## Aptove Router notifications (server → client)

All `bridge/*` notifications Aptove Router sends include a `bridgeAgentId` field in `params`. This allows the mobile client to continuously verify identity throughout the session, not just at connect time.

| Method | When sent | Key params |
|--------|-----------|------------|
| `bridge/identify` | First message after auth, before any ACP | `bridgeAgentId`, `cwd` |
| `bridge/requestPushToken` | After handshake, if push relay is configured | `bridgeAgentId` |
| `bridge/bufferReplayComplete` | After reconnect, once all buffered messages are sent | `bridgeAgentId`, `count` |
| `bridge/memoryLimitReached` | When `MEMORY.md` hits its size limit | `bridgeAgentId`, `currentBytes`, `limitBytes`, `message` |
| `bridge/remoteUserMessage` | When another device sends a prompt (multi-device sync) | `bridgeAgentId`, `senderId`, `content` |

---

## Client messages (client → Aptove Router)

The mobile client can send `bridge/*` messages to control Aptove Router features. These are intercepted by Aptove Router and never forwarded to the agent process.

| Method | Purpose | Key params |
|--------|---------|------------|
| `bridge/registerPushToken` | Register a device for push notifications | `platform`, `deviceToken`, `bundleId` |
| `bridge/unregisterPushToken` | Remove a device's push registration | `deviceToken` |
| `bridge/appendMemory` | Append a note to `MEMORY.md` | `text` |

---

## What happens on a mismatch

1. Aptove Router sends `bridge/identify` (or any subsequent `bridge/*` notification) with its `bridgeAgentId`.
2. The mobile client compares it against the stored `bridgeAgentId` for that agent.
3. They differ → client disconnects and shows a yellow warning banner in the chat view.
4. Auto-retry is suppressed for 5 minutes to avoid a rapid reconnect/disconnect loop.
5. The user scans the new Aptove Router instance's QR code to create a separate agent for the new project.

Normal reconnects (same Aptove Router instance restarting) are unaffected — the UUID is stable across restarts.
